# TrustCargo Pay — Supabase database

Schema, integrity rules and Row Level Security for TrustCargo Pay. The TypeScript domain model
(`src/domain/model.ts`, `src/domain/money.ts`, `src/domain/transaction/state-machine.ts`) is the
source of truth; these migrations map it to normalized Postgres tables.

TrustCargo Pay never holds funds. Payment tables only mirror instructions sent to, and events
reported by, a licensed payment partner. The MVP runs in **SIMULATION** mode only.

## Layout

| File | Content |
| --- | --- |
| `migrations/20261009000001_core_schema.sql` | Schemas `trustcargo` / `trustcargo_private`, domains (`currency_code`, `country_code`, `sha256_hex`), enums, the 40 business tables, the private `counters` and `demo_mfa_secrets` tables, FKs, CHECK/UNIQUE constraints, FK indexes, `updated_at` triggers, the optimistic lock on `transactions.version`, and DB-level guards for the transaction, payout and refund status transitions (`transaction_transition_allowed`, `settlement_transition_allowed`) |
| `migrations/20261009000002_ledger_integrity.sql` | Append-only ledger, audit and other append-only records, the deferred per-journal balance check, entry-versus-account currency check, reversal rules, `post_ledger_journal()` (service_role only), immutable `provider_events`, audit hash-chain verification, and the `ledger_account_balances` view |
| `migrations/20261009000003_rls.sql` | Grants, `trustcargo_private.*` RLS helpers, RLS on every table, policies, the private `trustcargo-documents` bucket (server-only: no `storage.objects` policy is created) |
| `migrations/20261010000001_simulated_partner.sql` | **SIMULATION ONLY.** Schema `trustcargo_sim`: the fake payment partner's own records (`instructions`, `transfers`, append-only `statement_lines`) with unique idempotency keys, RLS enabled, `service_role` only. Not TrustCargo's books |
| `tests/supabase_shim.sql` | Minimal stand-in for Supabase (roles, `auth`, `storage`) so the migrations run on plain PostgreSQL. **Never apply it to Supabase.** |
| `tests/rls_test.sql` | Self-checking test script that seeds data and asserts RLS, ledger and constraint behaviour |

## Conventions

- Nothing is created in `public` (checked by `tests/rls_test.sql`): the target Supabase project is
  shared with another application.
- The server's Postgres adapter (`src/server/adapters/postgres/tables.ts`) maps every entity of the
  TypeScript model losslessly: optional fields ↔ NULL, `bigint` ↔ `bigint`, dates without timezone
  shift, ordered child rows (`user_platform_roles.ordinal`, `reconciliation_items.ordinal`), polymorphic
  ids ↔ `*_user_id` / `*_organization_id`, `security_settings` single row ↔ TypeScript id `'default'`.
- Ids are UUIDv7 generated by the server (time-ordered: `order by id` = creation order).
- Money is always `amount_minor bigint` (integer minor units) plus `currency trustcargo.currency_code`
  (`char(3)` limited to CAD/USD/EUR/XOF). No column holds an amount as a float or numeric.
- `payment_accounts` stores only a masked identifier (at most 4 digits, enforced by a CHECK) and the
  partner's vault token. It never stores a raw account number.
- `provider_connections.webhook_secret_ref` stores the **name** of a secret, never its value.
- Audit hash chain: the application computes `hash = SHA-256(previous_hash + canonical event)`, the
  canonical event including `sequence` and `actor_id` (`'system'` / the provider name for non-user
  actors, so `actor_id` is text). The database serializes inserts with a lock and verifies that
  `sequence` = latest sequence + 1 and `previous_hash` = latest `hash`. The genesis event has
  sequence 1 and a previous hash of 64 zeros. A writer that loses a race gets SQLSTATE `40001` and
  must retry.
- `users` has no foreign key to `auth.users`: demo personas (`is_demo`) have no Supabase Auth
  account. A trigger requires a non-demo user's id to exist in `auth.users`; RLS keys on
  `auth.uid() = users.id`. The demo personas' fictitious TOTP secret lives in
  `trustcargo_private.demo_mfa_secrets` (service_role only, demo users only); real users' MFA is
  delegated to Supabase Auth.
- `updated_at`: where the TypeScript entity carries `updatedAt` (corridors, security settings,
  transactions, risk alerts, disputes, payment instructions, payouts, refunds), the writer's value is
  kept; other writers that leave it unchanged get `now()`. Elsewhere it is always `now()`.
- `payouts.requested_by` / `refunds.requested_by` hold a user id or `'system'` (automatic
  re-attempts); a generated `requested_by_user_id` keeps the foreign key to `users`.
- Optimistic locking: `update transactions set ..., version = version + 1 where id = $1 and version = $2`.
  If the writer does not bump `version`, the trigger bumps it. Any other change to `version` is
  rejected.

## Access model

- `anon` has no privileges at all.
- `authenticated` can read rows that RLS allows. It can also make a few self-service updates, each
  limited to specific columns:
  - `users`: `full_name`, `phone`, `city`, `locale`
  - `notifications`: `read_at`
  - `transactions`: `title`, only by the creator and only while the transaction is in `DRAFT`
  - `corridors` and `security_settings`: platform_admin only
- Every business write goes through the server with `service_role`. That includes state
  transitions, payments, ledger, audit, risk, documents and disputes. The server runs the
  TypeScript state machine and writes the audit event in the same database transaction. Its unit of
  work inserts ledger rows directly; SQL clients use `trustcargo.post_ledger_journal(...)`. Both
  paths go through the same balance, currency, reversal and append-only triggers.
- `trustcargo_private.counters` (gap-free counters such as transaction references) and
  `trustcargo_private.demo_mfa_secrets` are reachable by `service_role` only.
- `trustcargo_sim` (SIMULATION ONLY) holds the records of the fake payment partner played by
  `MockPaymentProvider`: its instructions, transfers and account statement. It is not TrustCargo's
  books (those are `payment_instructions`, `payouts`, `refunds`, `provider_events` and the ledger in
  `trustcargo`), has no foreign key to or from `trustcargo`, and stores references, amounts and
  statuses only. `anon` and `authenticated` have no privilege on it (not even `USAGE` on the schema);
  `service_role` can read and insert, update statuses only, and delete nothing. The server writes it
  in its own short transactions on a separate small pool, never inside a unit of work, so the fake
  partner behaves like an external system and survives restarts. Drop the schema once a licensed
  partner adapter replaces the mock (production refuses the mock provider).
- RLS helpers `trustcargo_private.has_platform_role`, `has_any_platform_role`, `is_org_member`,
  `party_roles`, `party_role`, `is_transaction_party` and `is_principal_party` are
  `SECURITY DEFINER`, `STABLE`, with `search_path = ''`. Because they read `transaction_parties`
  and `organization_members` outside RLS, the policies cannot recurse. A user is a party to a
  transaction when they have a `JOINED` party row, either directly or as a member of the party's
  organization.
- `INSPECTOR` and `FREIGHT_FORWARDER` parties never see payment instructions, payouts, refunds or
  disputes.
- A party sees a document only if they own it or one of their party roles is in
  `visible_to_roles`. `IDENTITY` documents are visible only to their owner and to
  compliance_analyst.
- Parties never see risk alerts, risk reviews, screening results or compliance holds.

## Apply to a Supabase project

```bash
supabase link --project-ref <project-ref>
supabase db push          # applies supabase/migrations in filename order
```

Locally with the Supabase CLI: `supabase start`, then `supabase db reset`.

These migrations have not been applied to a real Supabase project or the Supabase CLI stack yet.
Run them on a Supabase branch or staging project first.

## Tests (plain PostgreSQL 16)

```bash
npm run test:db           # = bash scripts/test-db.sh
```

Without `DATABASE_URL`, the script:

1. Creates a throwaway cluster in `.tmp/pgdata` on port 54329, with trust auth and the Unix socket
   in the data directory. When run as root it uses the `postgres` system user.
2. Applies `tests/supabase_shim.sql`, then the migrations in filename order.
3. Runs `tests/rls_test.sql` and removes the cluster.

With `DATABASE_URL` set (for example a CI `postgres:16` service), the script uses that database
instead. It must be an **empty** database, and the user must be a superuser so it can create the
roles and switch to them.

The migrations have been verified this way on PostgreSQL 16.15 with the shim: the script ends with
`ALL RLS/LEDGER TESTS PASSED`.

### Integration suite on the Postgres adapter

```bash
npm run test:pg           # = bash scripts/test-integration-pg.sh
```

Same cluster conventions (`.tmp/pgdata-integration`, port 54329, or the server of `DATABASE_URL`;
the shared bootstrap is `scripts/lib/pg-cluster.sh`). The script builds a template database (shim +
migrations), then runs `vitest` on `tests/integration`: every test app clones the template into its own
empty database, connects with `DATABASE_ROLE=service_role`, and drops it when the test ends.
`tests/integration/postgres-adapter.test.ts` (skipped without `TEST_PG_ADMIN_URL`) checks lossless
round trips of every table, ordering, error mapping, transactions, the audit chain after a restart,
cross-pool serialisation, privileges, and compares the SQL transition guards with the TypeScript
state machines. `tests/integration/simulated-partner.test.ts` runs the simulated partner store
contract on both stores and checks, on Postgres, that the fake partner's records survive a restart and
are shared between instances, that its writes never join a unit of work, and that idempotency holds
under concurrent requests from two pools.
