# ADR-0009 — Clés d'accès (WebAuthn), preuve MFA fraîche unifiée, anti-rejeu TOTP et codes de secours

| Champ  | Valeur                                                                                                                                                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Statut | Accepté                                                                                                                                                                                                                                                |
| Date   | 2026-10-11                                                                                                                                                                                                                                             |
| Portée | `apps/api/src/modules/auth` (`WebAuthnService`, `PasskeysService`, `MfaVerifierService`, `RecoveryCodesService`, `AuthCleanupService`), modèles `WebAuthnCredential`, `AuthChallenge`, `MfaRecoveryCode`, `User.mfaLastUsedStep`, tâche `AUTH_CLEANUP` |

## Contexte

Jusqu'à la phase 5, le second facteur était un code TOTP vérifié à quatre endroits différents (connexion, désactivation, autorisation de transfert, baisse des préférences de sécurité), chacun avec son propre appel `authenticator.verify`. Trois faiblesses en découlaient :

1. **Rejeu** : un code observé (épaule, proxy d'hameçonnage, journal mal filtré) restait valable pendant toute sa fenêtre de 30 s, autant de fois que voulu.
2. **Pas de recours** : la perte du téléphone imposait une intervention du support, sans procédure vérifiable.
3. **Facteur hameçonnable** : le TOTP se recopie sur un faux site ; les clés d'accès (WebAuthn / FIDO2), liées à l'origine, ne le permettent pas.

La plateforme reste un bac à sable (ADR-0003) : aucune de ces mesures ne déplace de fonds, mais elles protègent des comptes et des autorisations de transferts fictifs comme s'ils étaient réels, pour que la conception soit prête le jour où des partenaires agréés seront branchés.

## Décision

1. **Un seul point de vérification du second facteur : `MfaVerifierService`** (exporté par `AuthModule`, global). Toute opération sensible appelle `assertFreshProof(auth, preuve, finalité, erreur)` ; aucun autre module n'appelle `otplib` directement.
2. **Format unique de la preuve fraîche (step-up)** : le corps de l'opération protégée porte **soit** `mfaCode` (code TOTP à 6 chiffres **ou** code de secours), **soit** `passkeyAssertion` (assertion WebAuthn répondant à un défi `STEP_UP` obtenu par `POST /v1/auth/passkeys/step-up/options`). Il n'y a **pas de jeton de step-up intermédiaire** : le défi lui-même, à usage unique, lié à l'utilisateur **et** à la session, valable 5 minutes, joue ce rôle. Schéma partagé : `mfaProofShape` (`packages/shared/src/schemas/passkeys.ts`). Opérations concernées : autorisation de transfert, baisse des préférences de sécurité, révocation d'une clé d'accès, désactivation de la MFA, régénération des codes de secours, ajout d'une clé d'accès, étape MFA de la connexion (`code` / `passkeyAssertion`).
3. **Anti-rejeu TOTP** : le pas de temps accepté (`floor(t/30) + delta`, fenêtre otplib existante, instant figé par `authenticator.clone({ epoch })`) est enregistré atomiquement : `UPDATE "User" SET "mfaLastUsedStep" = pas WHERE id = … AND ("mfaLastUsedStep" IS NULL OR "mfaLastUsedStep" < pas)`. Zéro ligne modifiée ⇒ `401 MFA_CODE_REUSED`. Deux requêtes concurrentes avec le même code : une seule réussit. Le code de **confirmation d'activation** est **consommé** lui aussi (révision après la revue adversariale de la phase 6 : il ne peut pas être rejoué comme preuve de connexion dans la même fenêtre). Un nouveau secret (`mfa/setup`) remet l'historique à zéro.
   3 bis. **Activation de la MFA** (`POST /v1/auth/mfa/enable`) : code TOTP **et mot de passe actuel** (`currentPassword`). Une session seule ne peut pas installer son propre second facteur : un cookie volé permettrait sinon d'activer un TOTP contrôlé par l'attaquant, de recevoir les codes de secours, puis d'enregistrer une clé d'accès avec ce facteur (la preuve exigée par l'enregistrement devient le second facteur dès que la MFA est active). L'activation ferme les autres sessions du compte (ouvertes sans le nouveau facteur) et notifie le titulaire.
   3 ter. **Verrou par compte des codes** : chaque code TOTP ou de secours erroné incrémente `User.mfaFailedCount` ; au 5ᵉ échec consécutif, les codes sont refusés pendant 15 minutes (`423 ACCOUNT_LOCKED`, sans vérifier le code soumis, donc sans oracle ni consommation), les sessions pré-MFA du compte sont révoquées, l'événement est audité (`auth.mfa_locked`) et notifié. Un succès remet le compteur à zéro ; un code rejoué (`MFA_CODE_REUSED`) n'est pas compté. Le verrou ne dépend pas de l'adresse IP, que le client peut influencer (voir `TRUST_PROXY`). Les assertions de clé d'accès ne sont pas concernées (non devinables).
4. **Codes de secours** : 10 codes `XXXX-XXXX-XX` (base32, 50 bits) générés à l'activation de la MFA et à la régénération (preuve fraîche exigée, anciens codes supprimés), **affichés une seule fois**, stockés sous forme `HMAC-SHA-256(SESSION_SECRET, "dfn:mfa-recovery:v1:<userId>:<code>")` (une fuite de la base seule ne permet pas la force brute hors ligne). Acceptés partout où un code TOTP l'est ; usage unique par `UPDATE … WHERE usedAt IS NULL` ; inconnu ou déjà utilisé ⇒ `401 RECOVERY_CODE_INVALID`. Chaque utilisation est auditée (`auth.mfa_recovery_code_used`) et notifiée avec le nombre de codes restants. Désactiver la MFA supprime les codes.
5. **Clés d'accès (`@simplewebauthn/server` v14 / `@simplewebauthn/browser` v14)** :
   - RP ID `WEBAUTHN_RP_ID`, origines attendues `WEBAUTHN_ORIGINS` (liste séparée par des virgules) ; `userVerification: "required"` partout ; `residentKey: "preferred"` ; attestation `none` ; identifiant utilisateur WebAuthn = UUID du compte (jamais l'e-mail).
   - **Défis** (`AuthChallenge`) : 5 minutes, usage unique, liés à `purpose` (`REGISTRATION` | `AUTHENTICATION` | `STEP_UP`), à `userId` et `sessionId` (nuls pour la connexion sans mot de passe). Le défi est **brûlé avant toute vérification de signature** : une réponse ne peut jamais être retentée. Inconnu, expiré, réutilisé, autre session, autre finalité ⇒ même réponse `401 CHALLENGE_EXPIRED`.
   - **Enregistrement** : session complètement vérifiée **et** preuve fraîche avant l'émission du défi (`POST /registration/options`) : second facteur si la MFA est active, sinon mot de passe actuel (ou assertion d'une clé existante). Motif : une clé d'accès donne un accès durable équivalent à une MFA ; sans cette preuve, un simple cookie de session volé suffirait à installer un accès permanent — ce qui affaiblirait la sécurité existante. `excludeCredentials` = clés actives ; clé stockée avec clé publique COSE, compteur, transports, `deviceType`, `backedUp`, AAGUID. Audit + notification « Nouvelle clé d'accès ».
   - **Connexion sans mot de passe** : `POST /authentication/options` est public, limité en débit, accepte un e-mail facultatif mais **l'ignore** : `allowCredentials` vide (identifiants découvrables), aucune lecture en base, réponse de forme identique pour tout appelant — ni l'existence du compte ni celle de clés ne fuitent. `POST /authentication/verify` reproduit la connexion par mot de passe : verrouillage (423), statut (403), comptes supprimés/anonymisés refusés, clés révoquées refusées, échecs comptés dans le verrou de 15 minutes avec audit `auth.login_failed` (`method: "passkey"`, motif) et évaluation de risque `auth.login_failed`. Succès : session créée avec `mfaVerified = true` (une clé d'accès vérifiant l'utilisateur est un authentifiant multifacteur résistant à l'hameçonnage), `lastLoginAt`, audit `auth.login` (`method: "passkey"`).
   - **Compteur de signatures** : la bibliothèque vérifie la signature avec un compteur de référence 0, puis la règle WebAuthn §6.1.1 est appliquée sur une réponse **dont la signature est valide** (si l'un des compteurs est non nul, le nouveau doit être strictement supérieur) ; une régression est donc un vrai signal de clonage : refus, échec de connexion compté, notification « Clé d'accès suspecte ». Mise à jour du compteur par compare-and-set (`WHERE counter = ancien`) contre les usages concurrents. Les authentificateurs qui annoncent toujours 0 restent acceptés.
   - **Révocation** : `revokedAt` (jamais de suppression), preuve fraîche si la MFA est active (sinon la session suffit, pour qu'un utilisateur sans MFA ayant perdu son unique appareil puisse le révoquer), audit + notification « Clé d'accès révoquée ». Une clé d'un autre utilisateur ⇒ `404 PASSKEY_NOT_FOUND` (isolation).
   - Les sessions de clé API partenaire (`sessionId = "api:…"`) ne peuvent pas mener de cérémonie WebAuthn.
6. **Tâche `AUTH_CLEANUP`** (enregistrée par `AuthCleanupService` sur `JobRegistry`) : purge des défis expirés ou utilisés (une ligne absente ne peut plus être utilisée : la recherche exige la ligne) et des sessions terminées (expirées ou révoquées) depuis plus de 7 jours ; idempotente, par lots bornés (20 × 500 lignes par table et exécution, `truncated` signale un reliquat).

## Conséquences

Positives : un code TOTP n'est plus rejouable, même en concurrence ; la perte du téléphone a un recours en libre-service traçable ; les utilisateurs peuvent se connecter sans mot de passe avec un facteur résistant à l'hameçonnage ; toutes les opérations sensibles partagent la même vérification, les mêmes codes d'erreur et le même audit ; l'énumération de comptes par l'API des clés d'accès est impossible.

Négatives : un utilisateur qui saisit le même code deux fois dans la même fenêtre de 30 s (par exemple après une erreur métier survenue après la vérification) doit attendre le code suivant ou utiliser une clé d'accès ; changer `SESSION_SECRET` invalide les codes de secours (comme les sessions) — à régénérer après rotation ; l'option d'enregistrement exige une preuve, une friction de plus pour l'utilisateur ; `AuthChallenge` reçoit une ligne par demande d'options publique (borné par la limite de débit et purgé par `AUTH_CLEANUP`). Cinq codes erronés bloquent les codes du compte 15 minutes, y compris pour son titulaire légitime (qui garde ses clés d'accès) : un attaquant connaissant le mot de passe peut provoquer ce blocage, au prix d'une notification au titulaire.

## Alternatives

| Alternative                                                            | Raison du rejet                                                                                                                                                        |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Jeton de step-up court (`POST /step-up/verify` → jeton à usage unique) | Un secret de plus à stocker, transmettre et invalider ; aucun modèle dédié dans le schéma ; le défi `STEP_UP` lié à la session offre la même garantie                  |
| Anti-rejeu en mémoire (cache des codes utilisés)                       | Perdu au redémarrage, non partagé entre réplicas ; la colonne `mfaLastUsedStep` + `UPDATE` conditionnel est atomique et multi-instance                                 |
| Codes de secours hachés en SHA-256 simple ou argon2                    | SHA-256 nu : 50 bits attaquables hors ligne après une fuite de la base ; argon2 : 10 vérifications lentes par tentative. HMAC avec secret serveur : ni l'un ni l'autre |
| `allowCredentials` rempli à partir de l'e-mail fourni à la connexion   | Révèle l'existence du compte et de ses clés (énumération) ; les identifiants découvrables rendent l'e-mail inutile                                                     |
| Enregistrement d'une clé avec la seule session                         | Un cookie volé deviendrait un accès permanent contournant mot de passe et TOTP                                                                                         |
| Considérer une clé d'accès comme « MFA activée » (`mfaEnabled`)        | Changerait le parcours de connexion par mot de passe de tous les porteurs de clé ; reporté — la MFA reste le TOTP, la clé d'accès est un facteur accepté partout       |

## Révision

À revoir avant toute mise en production réelle : politique d'attestation (AAGUID autorisés via le service de métadonnées FIDO), lien avec la vérification d'identité forte exigée par un partenaire agréé, et rotation de `SESSION_SECRET` (dérivation d'une clé dédiée aux codes de secours depuis le trousseau).
