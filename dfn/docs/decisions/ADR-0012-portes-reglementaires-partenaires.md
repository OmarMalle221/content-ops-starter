# ADR-0012 — Registre des portes réglementaires (R1–R10) et adaptateurs partenaires de référence non activables

| Champ  | Valeur                                                                                                                                                                                                                                                                                                                        |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Statut | Accepté                                                                                                                                                                                                                                                                                                                       |
| Date   | 2026-10-11                                                                                                                                                                                                                                                                                                                    |
| Portée | `apps/api/src/modules/gates`, modèles `RegulatoryGate` / `RegulatoryGateEvent`, `packages/shared/src/schemas/gates.ts`, fabriques de `packages/compliance` et `packages/payment-adapters`, adaptateurs `HttpReference*`, variables `KYC_PROVIDER`, `SANCTIONS_PROVIDER`, `PAYMENT_PROVIDER`, `FX_PROVIDER`, `PAYOUT_PROVIDER` |

## Contexte

La feuille de route (ROADMAP §10) fixe dix portes réglementaires (R1 à R10) à franchir avant toute phase « live ». Jusqu'ici, leur suivi vivait uniquement dans des documents (`AUTHORIZATIONS_CHECKLIST.md`) : aucune trace dans l'application de qui a fait avancer quoi, ni de double validation. En parallèle, la préparation des partenaires (KYC/KYB, sanctions, change, versements) demande de rendre concret ce qu'un fournisseur réel devrait respecter (authentification, idempotence, signatures, fraîcheur des taux) **sans** jamais rendre un tel fournisseur atteignable : le build reste `DFN_MODE=sandbox` (ADR-0003) et les fabriques refusent tout code non sandbox (ADR-0008).

Deux risques sont à éviter : (1) qu'un registre « tout vert » soit perçu — ou codé — comme un interrupteur vers le réel ; (2) qu'un adaptateur HTTP prêt à l'emploi soit activable par simple variable d'environnement.

## Décision

1. **Registre de suivi en base** : la table `RegulatoryGate` contient les dix portes définies dans `REGULATORY_GATES` (`@dfn/shared`). `RegulatoryGatesService.ensureDefaults()` crée les portes manquantes au démarrage du module et paresseusement avant chaque lecture/écriture (les tests tronquent la table) ; il ne modifie jamais statut, notes, référence de preuve ni approbations (au démarrage, seuls les champs de définition — intitulé, juridiction, document, niveau — sont resynchronisés avec le code).
2. **Cycle de vie explicite** (`regulatoryGateMachine`) : `NOT_STARTED → IN_PROGRESS` ; `IN_PROGRESS → IN_PROGRESS` (avancement documenté), `PENDING_SECOND_APPROVAL`, `REVOKED` ; `PENDING_SECOND_APPROVAL → SATISFIED | REVOKED` ; `SATISFIED → REVOKED` ; `REVOKED → IN_PROGRESS`. Une approbation exige l'état `IN_PROGRESS`.
3. **Règle des quatre yeux** : la première approbation (note + référence de preuve obligatoires) fixe `firstApprover` et place la porte en `PENDING_SECOND_APPROVAL` ; la seconde, par un **autre** administrateur, fixe `secondApprover` et place la porte en `SATISFIED`. Le même approbateur est refusé (`GATE_SAME_APPROVER`, 409), de même que deux comptes dont l'un a modifié le rôle de l'autre, dans un sens comme dans l'autre (un ADMIN ne peut pas promouvoir un compte qu'il contrôle pour approuver deux fois, que ce compte approuve en premier ou en second). La porte conserve la note et la référence de preuve du premier approbateur, que le second approuve ; la note et la référence de revue du second restent dans l'événement et l'audit. La révocation efface les deux approbations et la référence de preuve ; l'historique est conservé.
4. **Traçabilité** : chaque transition écrit, dans une même transaction avec contrôle de concurrence (comparaison sur statut, horodatage et premier approbateur), une ligne `RegulatoryGateEvent` et une ligne `AuditLog` (`gate.progress`, `gate.first_approval`, `gate.second_approval`, `gate.revoke`, référence de preuve en métadonnée), puis notifie tous les administrateurs actifs.
5. **Droits** : lecture `ADMIN_GATES_VIEW` (conformité et administrateurs), écriture `ADMIN_GATES_MANAGE` (administrateurs). Les actions proposées sont pilotées par le serveur (`nextActions`) : un compte conformité ne voit aucun contrôle.
6. **Suivi uniquement** : chaque réponse porte `trackingOnly: true` et l'avertissement FR/EN « aucun statut ne permet d'activer des fonds réels ; DFN_MODE reste sandbox ». Aucun code ne lit le statut d'une porte pour autoriser quoi que ce soit.
7. **Garde d'activation** : `ProviderActivationService.assertProviderActivatable(kind, code)` refuse **toujours** un code non sandbox (`PROVIDER_NOT_ACTIVATABLE`), y compris si toutes les portes requises sont satisfaites, et liste en détail les portes requises avec leur statut courant : KYC/SANCTIONS → R1, R2, R7, R8 ; PAYMENT/PAYOUT → R1, R3, R4, R5, R6, R7, R8, R9 ; FX → R1, R3, R4, R6, R8 (`PROVIDER_REQUIRED_GATES`). `GatesModule.onModuleInit` l'applique aux cinq variables `*_PROVIDER` : l'API refuse de démarrer avec un message explicite. Les fabriques des paquets lèvent de leur côté `ProviderNotActivatableError` (même code, mêmes portes, message « sandbox-only »).
8. **Adaptateurs de référence** : `HttpReferenceKycProvider`, `HttpReferenceSanctionsProvider` (`@dfn/compliance`), `HttpReferenceFxRateProvider`, `HttpReferencePayoutProvider` (`@dfn/payment-adapters`) implémentent un contrat REST générique documenté (`docs/architecture/PARTNER_ADAPTERS.md`). Ils portent un nom générique « reference » (jamais une marque), ne sont **enregistrés dans aucune fabrique**, ne sont lus par **aucune variable d'environnement** et ne sont construits que par les tests contractuels contre un serveur `node:http` local. Leurs résultats KYC ne produisent jamais de statut « réussi » : une décision `APPROVED` du fournisseur devient `PENDING` avec `requiresManualReview: true`.
9. **Interface de versement** : `PayoutProvider` (création idempotente, consultation, rappels de statut signés) avec `SandboxPayoutProvider` (en mémoire, aucun réseau) et la fabrique `createPayoutProvider(PAYOUT_PROVIDER)`, sandbox uniquement.

## Conséquences

Positives : le suivi des portes devient vérifiable (qui, quand, quelle preuve) et soumis à une double validation ; la frontière sandbox reste codée en dur et testée (fabriques, garde au démarrage, garde même avec toutes les portes satisfaites) ; les exigences techniques d'un futur partenaire (authentification, idempotence, signatures horodatées, délais, reprises, fraîcheur et plausibilité des taux en arithmétique entière) sont exprimées par des tests exécutables ; l'écran d'administration donne une vue unique des portes et des fournisseurs configurés.

Négatives : risque de lecture erronée d'un registre « satisfait » comme une autorisation — atténué par l'avertissement permanent, `trackingOnly` et la garde ; les références de preuve sont du texte libre (aucun dépôt de fichier, la preuve reste dans le coffre documentaire de la conformité) ; la table d'événements n'a pas de colonne dédiée à la référence de preuve, qui est lue depuis les métadonnées d'audit ; les adaptateurs de référence n'engagent aucun fournisseur réel et devront être adaptés au contrat effectivement signé.

## Alternatives

| Alternative                                                                    | Raison du rejet                                                                                                                     |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Activer automatiquement un fournisseur quand ses portes sont `SATISFIED`       | Transforme un outil de suivi en interrupteur vers le réel ; contraire à ADR-0003 et à la ligne TR-10 (revue à deux personnes + ADR) |
| Une seule approbation par porte                                                | Pas de contrôle croisé sur des décisions réglementaires engageantes                                                                 |
| Déposer les preuves (avis, contrats) dans l'application                        | Documents juridiques sensibles hors du coffre de la conformité ; surface d'attaque et rétention inutiles                            |
| Adaptateurs HTTP sélectionnables par variable d'environnement « en mode test » | Un changement de configuration suffirait à appeler un tiers ; frontière sandbox/réel floue (ADR-0003, ADR-0008)                     |
| Nommer les adaptateurs d'après un fournisseur existant                         | Laisserait croire à un partenariat ou à une intégration validée                                                                     |
| Garder le suivi uniquement dans `AUTHORIZATIONS_CHECKLIST.md`                  | Pas d'horodatage fiable, pas de double validation, pas de lien avec la garde d'activation                                           |

## Révision

Revoir cet ADR à la signature du premier contrat partenaire : le contrat réel remplacera le contrat de référence correspondant, et la sortie du mode sandbox fera l'objet d'un ADR distinct signé conformément au §9 de `AUTHORIZATIONS_CHECKLIST.md` — le registre n'en sera qu'une pièce justificative.
