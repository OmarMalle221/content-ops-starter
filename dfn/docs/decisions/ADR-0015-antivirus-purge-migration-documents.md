# ADR-0015 — Antivirus des téléversements, purge différée selon la rétention et migration local → S3

| Champ  | Valeur                                                                                                                                                                                                                                                                                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Statut | Accepté (complète l'ADR-0010 ; remplace son point « la copie des documents d'un pilote vers l'autre n'est pas automatisée »)                                                                                                                                                                                                                                      |
| Date   | 2026-10-12                                                                                                                                                                                                                                                                                                                                                        |
| Portée | `apps/api/src/common/antivirus/`, module `documents` de l'API (téléversement, suppression, `DocumentStorageService`, tâches `DOCUMENT_PURGE` et `STORAGE_MIGRATION`, console `/v1/admin/storage`), modèle `Document` (`scanStatus`, `scanEngine`, `scannedAt`, `blobPurgedAt`), variables `ANTIVIRUS_*`, `CLAMD_*`, `DOCUMENT_PURGE_GRACE_DAYS`, `STORAGE_DRIVER` |

## Contexte

Trois écarts restaient ouverts sur les documents chiffrés (ADR-0006, ADR-0010) :

1. **Aucune analyse antivirus** : un fichier téléversé n'était contrôlé que sur son type (liste blanche MIME et octets magiques). Un PDF piégé était stocké puis servi tel quel à l'autre partie de la transaction ou à la conformité.
2. **Suppression immédiate du blob** (`SECURITY.md`, écart « Moyen ») : supprimer un document effaçait aussitôt son contenu chiffré, sans attendre `retentionUntil` (7 ans par défaut, obligations LBC/FT à confirmer). La conformité perdait des pièces qu'elle doit pouvoir produire.
3. **Bascule `local` → `s3` incomplète** : les nouveaux documents allaient sur S3, mais les anciens restaient sur le disque d'une réplique ; impossible de retirer le volume local ni de passer à plusieurs hôtes sans copie manuelle.

La plateforme reste un bac à sable (ADR-0003) : aucun moteur antivirus n'est imposé, et ce qui est simulé ne doit jamais être présenté comme une protection réelle.

## Décision

### 1. Antivirus : modèle de fournisseurs, analyse avant stockage, échec fermé

- Interface `Scanner { engine; scan(octets) → { verdict: CLEAN | INFECTED, signature? } }`, trois fournisseurs choisis par `ANTIVIRUS_PROVIDER` :
  - `sandbox` (défaut du bac à sable) : **simulation** qui ne reconnaît que la chaîne de test EICAR, n'importe où dans le fichier, et rien d'autre. Moteur enregistré `sandbox-eicar`. Le journal de démarrage, la documentation et l'interface (badge « simulation » et infobulle « ne détecte que le fichier de test EICAR ») le disent ; ce n'est jamais présenté comme une protection ;
  - `clamd` : démon ClamAV en TCP, protocole `INSTREAM` (`zINSTREAM\0`, segments préfixés de leur longueur sur 4 octets gros-boutiens, segment vide final, réponse terminée par NUL : `stream: OK`, `stream: <signature> FOUND`, `… ERROR`). Contre-pression respectée à l'écriture, une échéance unique `ANTIVIRUS_TIMEOUT_MS` (connexion, envoi, verdict) ;
  - `none` : aucune analyse ; le document est enregistré `SKIPPED` (jamais « sain »).
- **L'analyse a lieu après les contrôles d'accès et de type, et avant tout stockage.** `INFECTED` → `422 DOCUMENT_INFECTED`, rien n'est écrit (ni blob ni ligne), audit `document.rejected_infected` avec le moteur et le **nom de signature** seulement (plus type, taille, SHA-256 — jamais le nom de fichier ni le contenu).
- **Échec fermé** : sans verdict (démon injoignable, délai dépassé, `INSTREAM size limit exceeded`, erreur du moteur, connexion coupée, réponse illisible), le téléversement est refusé en `503 SCAN_UNAVAILABLE` (`details.reason`), sauf fournisseur `none`. Un antivirus en panne bloque donc les téléversements plutôt que de laisser passer des fichiers non analysés.
- Verdict enregistré sur la ligne (`scanStatus`, `scanEngine`, `scannedAt`) et dans l'audit `document.uploaded` ; les documents antérieurs restent `NOT_SCANNED`. Un document marqué `INFECTED` n'est **jamais servi** : pas de lien de téléchargement dans les DTO, `409 DOCUMENT_INFECTED` (audit `document.download_refused`) sans même déchiffrer le blob.

### 2. Purge différée, alignée sur la rétention

- **Supprimer un document ne fait plus que la suppression logique** (`deletedAt`) : le blob chiffré est conservé, l'audit `document.deleted` et la réponse indiquent `purgeAfter`. Un document supprimé n'est plus téléchargeable ; `GET /v1/documents/deleted` liste les documents supprimés du même périmètre que la liste courante avec l'état de leur fichier (`RETAINED` jusqu'à `purgeAfter`, puis `PURGED`).
- La tâche **`DOCUMENT_PURGE`** (enregistrée par `DocumentsModule`) détruit le blob quand `max(deletedAt + DOCUMENT_PURGE_GRACE_DAYS, retentionUntil)` est passé, **jamais** tant que le document est une pièce : preuve de jalon (quelle qu'elle soit), preuve ou pièce jointe de message d'un litige qui n'est pas `CLOSED`. La ligne (métadonnées, SHA-256) est conservée et horodatée `blobPurgedAt`.
- Par document : suppression du blob (et d'une éventuelle copie temporaire de rotation), puis horodatage par comparaison-échange sur l'emplacement (`storageDriver`, `storageKey`, `blobPurgedAt` nul) — un document déplacé entre-temps par la migration est laissé à l'exécution suivante —, puis seconde suppression contre un remplacement de rotation concurrent. Une ligne n'est horodatée que si la purge (ou une suppression antérieure à cette décision) a détruit son blob, **jamais parce que le blob est introuvable** :
  - le stockage de chaque pilote est sondé une fois par exécution (`healthCheck`) ; injoignable, mal configuré ou non inscriptible (volume non monté, mauvais `STORAGE_DIR`, bucket inexistant, droits), ses documents sont comptés `failed` (`STORAGE_UNREACHABLE`, `STORAGE_MISCONFIGURED`, …) sans qu'aucun blob soit cherché ni aucune ligne horodatée — une purge qui prendrait l'absence pour une destruction marquerait en masse des lignes dont le chiffré subsiste, hors de portée de toute tâche ;
  - un blob absent d'un stockage sain n'est enregistré purgé (`missing`, audit `document.blob_missing`) que si la suppression du document est antérieure à cette décision (audit `document.deleted` sans `blobRetained`) — la règle qu'appliquent déjà la rotation et la migration ; toute autre absence est une anomalie comptée `failed` (`STORAGE_NOT_FOUND`), réessayée à chaque exécution et visible dans `remaining` jusqu'à ce qu'un opérateur la traite (restauration des blobs, ou enregistrement manuel une fois la perte confirmée : runbook §11).
- La seconde suppression ne couvre pas une réplique de rotation qui s'arrête entre son remplacement et sa comparaison-échange (ni une réplique de migration qui s'arrête entre sa copie S3 et sa bascule) : la copie resterait derrière une ligne purgée, hors du filtre de toutes les tâches. Chaque exécution rebalaye donc (`reswept`) l'emplacement enregistré — et, pendant une migration, le même `storageKey` sur S3 — des lignes purgées depuis le début de l'exécution précédente : seconde suppression idempotente, bornée à 1 000 lignes, au mieux.
- Idempotente et reprenable : les lignes purgées ne correspondent plus au filtre ; exécutions bornées (pages de 100, 1 000 documents, 5 min, signal de bail) et parcours à partir d'un identifiant aléatoire (des échecs répétés ne bloquent pas la file). Chaque page est auditée par organisation (`document.blobs_purged` : identifiants purgés, absents, nombre d'échecs) ; le résumé de l'exécution donne les compteurs (`purged`, `missing`, `raced`, `failed`, `remaining`).
- La rotation des clés rescelle aussi les blobs des documents supprimés **conservés** (ils doivent rester lisibles pendant la rétention) et sa comparaison-échange porte sur `blobPurgedAt` et l'emplacement, non plus sur `deletedAt`. Un document supprimé avant cette décision (reconnu à son audit `document.deleted` sans `blobRetained`) n'a plus de blob : la rotation l'enregistre purgé (`document.blob_missing`) au lieu d'échouer à chaque exécution et d'épingler sa clé. Toute autre absence de blob (document vivant, blob conservé) reste une anomalie signalée — par exemple un stockage pointé vers le mauvais bucket — et n'est jamais masquée.

### 3. Migration `local` → `s3` sûre

- La tâche **`STORAGE_MIGRATION`** refuse de s'exécuter sans `STORAGE_DRIVER=s3` (exécution planifiée : sans effet ; exécution manuelle : échec explicite ; console : `409 NOT_AVAILABLE`) et sans destination saine (`HeadBucket`).
- Par document (vivant ou supprimé-conservé ; jamais purgé) : lecture du blob local et **vérification complète** (authentification GCM et SHA-256 du clair égal à `Document.sha256`) — un contenu corrompu n'est jamais copié ; écriture des mêmes octets scellés sur S3 puis **relecture : SHA-256 des octets scellés relus = SHA-256 des octets locaux**, sinon la copie est supprimée ; bascule de la ligne par **comparaison-échange** (`storageDriver = local`, même `storageKey`, même `encryptionKeyId`, `blobPurgedAt` nul) — une rotation ou une purge concurrente fait échouer la bascule et la copie S3 est supprimée ; **ensuite seulement**, suppression de la copie locale.
- Un téléchargement qui avait lu la ligne avant la bascule et ne trouve plus le blob local relit la ligne et suit le document sur S3. Un document supprimé avant cette décision et sans blob est enregistré purgé (même règle que la rotation) ; tout autre blob absent est compté `missing` et reste en attente.
- Mode **essai à blanc** : le cadre des tâches n'accepte pas de paramètres ; le drapeau voyage dans `triggeredBy` (`manual:<utilisateur>:dry-run`), comme le filtre d'usage de la rotation des clés. `POST /v1/admin/storage/migration {dryRun}` (permission `admin:keys`) lance l'une ou l'autre exécution par `MaintenanceService` (même bail et même historique) ; l'essai ne fait que l'étape de vérification et rapporte nombres et octets. `GET /v1/admin/storage` donne les compteurs (blobs par pilote, verdicts, conservés, purgeables, purgés, migration en attente).
- Bornée (pages de 25, 200 documents, 5 min), reprenable, auditée par page et par organisation (`document.blobs_migrated`) et par exécution (`storage.migration_run`). Les tâches `DOCUMENT_PURGE` et `STORAGE_MIGRATION` restent réservées à `admin:keys` dans la console des tâches.

## Conséquences

Positives : aucun fichier n'est stocké sans verdict quand un antivirus est configuré, et une panne de l'antivirus ne dégrade jamais silencieusement la protection ; la simulation du bac à sable permet d'éprouver le chemin de refus de bout en bout (fichier EICAR) sans prétendre protéger ; les pièces supprimées restent produisibles pendant la rétention et les preuves de litige ouvert ne disparaissent jamais ; le volume local peut être vidé document par document, chaque étape étant vérifiée et réversible jusqu'à la bascule de la ligne ; plusieurs réplicas peuvent exécuter rotation, purge, migration et téléchargements en parallèle (baux par tâche, comparaison-échange par ligne).

Négatives : l'analyse ajoute la latence du moteur au téléversement et un point de défaillance (d'où l'échec fermé et l'alerte au démarrage) ; un démon ClamAV consomme 1 à 3 Go de mémoire et doit recevoir ses mises à jour de signatures ; la limite `StreamMaxLength` de clamd doit suivre `MAX_UPLOAD_MB` ; les blobs supprimés occupent l'espace de stockage pendant toute la rétention (7 ans par défaut) et restent liés à leur clé ; les documents supprimés **avant** cette décision n'ont plus de blob, ils sont horodatés purgés au moment où la purge, la migration ou la rotation les rencontre ; un blob conservé qui a disparu bloque sa ligne en `failed` jusqu'à intervention (voulu : l'obligation d'effacement n'est jamais déclarée remplie sans destruction) ; chaque exécution de la purge relit les lignes purgées depuis l'exécution précédente (`blobPurgedAt`, non indexé) et émet jusqu'à 1 000 suppressions idempotentes de plus ; aucune migration inverse `s3` → `local` n'est automatisée (procédure manuelle dans le runbook).

## Alternatives

| Alternative                                                        | Raison du rejet                                                                                                                                                |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Analyse asynchrone après stockage (quarantaine, verdict ultérieur) | Le fichier existe et peut être lu avant le verdict ; états intermédiaires à gérer partout ; reportée à des moteurs plus lents (bac à sable dynamique)          |
| Échec ouvert (stocker sans verdict si l'antivirus est en panne)    | Une panne, ou une attaque qui sature le démon, désactiverait la protection sans bruit ; le choix explicite est `ANTIVIRUS_PROVIDER=none`, enregistré `SKIPPED` |
| Analyse côté navigateur ou par le fournisseur de stockage          | Contournable par le client ; dépend de l'hébergeur ; voit du clair que le stockage ne doit jamais voir (chiffrement applicatif, ADR-0010)                      |
| Purge à `deletedAt + délai` seulement                              | Ignore les obligations de conservation (`retentionUntil`) et les preuves de litige                                                                             |
| Règles de cycle de vie du bucket (expiration S3)                   | Ne connaît ni la rétention par document ni les litiges ; ne couvre pas le pilote local ; aucune trace dans l'audit                                             |
| Migration par copie en masse (`mc mirror`) puis `UPDATE` global    | Pas de vérification par document, fenêtre où lignes et blobs divergent, aucune reprise propre ni coexistence avec rotation et purge                            |
| Variable d'environnement pour l'essai à blanc                      | Redémarrage nécessaire pour changer de mode ; le drapeau par exécution reste tracé dans `MaintenanceRun.triggeredBy`                                           |

## Détails de mise en œuvre

| Élément                      | Choix                                                                                                                                                                                                                                                                  |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chaîne EICAR dans le code    | Assemblée à partir de deux moitiés : le fichier source n'est pas signalé par l'antivirus d'un poste de développement                                                                                                                                                   |
| Signature                    | Caractères `[A-Za-z0-9._:/+()-]`, 128 au plus ; réponse clamd plafonnée à 4 Kio                                                                                                                                                                                        |
| Codes d'erreur               | `422 DOCUMENT_INFECTED` (téléversement), `409 DOCUMENT_INFECTED` (téléchargement d'un document marqué), `503 SCAN_UNAVAILABLE` (`UNREACHABLE`, `TIMEOUT`, `SIZE_LIMIT`, …)                                                                                             |
| Date de purge                | `purgeAfter = max(deletedAt + DOCUMENT_PURGE_GRACE_DAYS, retentionUntil)` ; `retentionUntil` = téléversement + 7 ans                                                                                                                                                   |
| Pièces qui bloquent la purge | Toute preuve de jalon ; preuve ou pièce jointe de message d'un litige non `CLOSED`                                                                                                                                                                                     |
| Tests                        | `apps/api/test/antivirus.test.ts` (faux démon clamd INSTREAM : sain, infecté, erreur, délai, segments, limite de taille), `document-purge.test.ts`, `storage.test.ts`, `s3-store.test.ts` (suite réelle avec `S3_TEST_ENDPOINT`, création du bucket, migration réelle) |

## Révision

Revoir cette décision au choix d'un moteur antivirus de production (ou d'une analyse dynamique asynchrone), à la confirmation juridique des durées de conservation par type de document (UEMOA, Guinée, Canada), si le volume des blobs conservés impose une classe de stockage froide, ou si une migration entre deux buckets S3 devient nécessaire.
