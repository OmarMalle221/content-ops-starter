# ADR-0016 — Observabilité : métriques Prometheus, traces W3C et alertes

| Champ  | Valeur                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Statut | Accepté (lève la réserve « pas encore de point de collecte de métriques » du RUNBOOK §9)                                                                                                                                                                                                                                                                                                                                     |
| Date   | 2026-10-17                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Portée | `apps/api/src/modules/observability/` (`GET /metrics`, instrumentation HTTP, jauges métier, contexte de trace), bloc `LoggerModule` d'`app.module.ts`, en-tête `traceparent` des webhooks sortants (`api-platform/webhook-http.ts`), variables `METRICS_ENABLED` / `METRICS_TOKEN`, profil Compose `observability` (Prometheus, Grafana, secret `metrics_token`), `infra/observability/`, `docs/operations/OBSERVABILITY.md` |

## Contexte

Jusqu'à la phase 6, l'exploitation lisait les indicateurs dans les journaux JSON et dans les consoles d'administration (`/admin/jobs`, `/admin/keys`, réconciliation). Aucun point de collecte ne permettait de tracer une latence, un taux d'erreur, une file de webhooks qui enfle ou une tâche qui ne tourne plus — le RUNBOOK §9 le notait comme prérequis « avant toute phase live ». Les phases 6 et 7 ont ajouté des mécanismes dont la défaillance est silencieuse : planificateur distribué par baux (ADR-0011), cycle de vie des clés KMS (ADR-0014), antivirus et purge différée (ADR-0015), nouvelles tentatives de webhooks, SLA de la file de revue. Enfin, relier une requête à ce qu'elle déclenche (journaux des services, webhook reçu par un partenaire) reposait sur le seul `X-Request-Id`, inconnu des partenaires.

Contraintes : bac à sable (ADR-0003 — rien ne doit laisser croire à une surveillance de fonds réels), plusieurs répliques possibles de l'API, aucune dépendance obligatoire à un service externe, et une exposition qui ne devienne ni une fuite d'information ni une charge sur la base.

## Décision

### 1. Métriques Prometheus, un registre par processus

- `prom-client` avec un registre propre à l'application (pas le registre global : les tests démarrent plusieurs applications côte à côte), métriques processus par défaut préfixées `dfn_`, `dfn_api_info` pour identifier la réplique.
- HTTP : `dfn_http_requests_total{method,route,status}` et l'histogramme `dfn_http_request_duration_seconds{method,route}`, enregistrés par un middleware du module d'observabilité sur l'événement `finish` de la réponse. `route` est le **gabarit** enregistré par le routeur Express (`req.route.path`, posé avant les gardes) : jamais l'URL, jamais un identifiant ; les requêtes sans route sont `unmatched`, l'interface OpenAPI `/docs`, le point de collecte `/metrics`. La cardinalité est ainsi bornée par le nombre de routes, quoi qu'envoie un client.
- `GET /metrics` est servi **par un middleware, hors `/v1`, avant tout garde** : le garde de session interroge la base pour tout `Bearer`, le limiteur de débit interroge Redis ; une collecte ne doit dépendre ni de l'un ni de l'autre pour rester un signal de vie du processus. `METRICS_ENABLED=false` ne l'enregistre pas (404 ordinaire).
- Accès décidé par une fonction pure testée isolément : `METRICS_TOKEN` défini → `Authorization: Bearer` comparé à temps constant (401 sinon, loopback compris) ; absent → pair TCP loopback uniquement (`socket.remoteAddress`, jamais `X-Forwarded-For` pour accorder) **et** requête non relayée : tout en-tête de relais (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `Via`) vaut refus, parce qu'un proxy sur la même machine — la réécriture `/api/*` de l'application web en `pnpm dev`, un reverse proxy local — est lui-même un pair loopback et prêterait sa localité à n'importe quel client distant (403 sinon).

### 2. Jauges métier calculées à la collecte, avec cache

- Tâches de maintenance enregistrées par la réplique (`dfn_maintenance_job_registered`, lu dans le `JobRegistry`) et dernière exécution de chacune (statut, âge, durée, âge du dernier succès), livraisons de webhooks par statut et plus ancienne livraison due, file de revue (ouvertes, hors SLA, en retard, par sévérité), demandes de lien en attente, transferts par statut, documents par verdict antivirus, clés gérées par usage et statut, dernière réconciliation du registre (statut — séries présentes à 0 avant toute réconciliation —, âge, écarts, comptes vérifiés). Les séries « enregistrée » et « statut à 0 » existent pour que les règles distinguent **jamais exécuté** (planificateur jamais démarré, base restaurée sans historique) de **collecteur en échec** (aucune série) : une absence de série ne peut pas déclencher une alerte d'obsolescence.
- Lues en base dans les `collect()` des jauges, **au plus une fois par 15 s et par réplique** ; les collectes concurrentes attendent le même rafraîchissement en cours ; chaque rafraîchissement est borné à 5 s (sous le `scrape_timeout` de Prometheus).
- Collecteurs exécutés **en série**, chacun dans **une transaction** portant un `statement_timeout` égal au budget restant (`set_config(..., is_local)`), attente de connexion bornée à 1 s, et **vol unique** par collecteur (une transaction précédente encore ouverte → le collecteur est sauté, pas relancé) : un rafraîchissement ne tient jamais plus d'une connexion du pool, une requête bloquée est annulée par le serveur et rend sa connexion ; les collectes ne peuvent pas transformer une base lente en épuisement du pool pour les requêtes de l'API.
- Un collecteur qui échoue, est annulé ou sauté **retire ses séries** et incrémente `dfn_metrics_collect_errors_total{collector}` ; les autres collecteurs et les métriques HTTP / processus sont servis. Pas de valeur périmée présentée comme actuelle, pas de page qui tombe avec la base.
- Toutes les répliques exposent les mêmes valeurs métier : règles et tableau de bord les agrègent avec `max()` ; l'étiquette de tâche est `job_name` pour ne pas entrer en conflit avec le `job` de Prometheus.

### 3. Traces W3C sans backend

- `traceparent` entrant valide (niveau 1, identifiants non nuls, hexadécimal minuscule, version ≠ `ff`, versions futures lues sur leurs quatre premiers champs) → même `trace_id`, nouveau `span_id`, seul le bit « échantillonné » conservé ; sinon nouvelle trace échantillonnée. Contexte mémorisé sur la requête (`WeakMap`) et porté par `AsyncLocalStorage` pour tout ce que la requête déclenche, réponse comprise.
- Renvoyé en en-tête de réponse sur toute réponse ; `trace_id` / `span_id` liés au journal de requête pino (`customProps`) donc présents sur chaque ligne de la requête ; `X-Request-Id` / `req.id` conservés.
- Webhooks sortants : `traceparent` avec un span enfant du contexte courant, ou une nouvelle trace hors requête (nouvelles tentatives du planificateur) ; un appelant peut fournir le sien. Un partenaire corrèle ainsi ses journaux aux nôtres sans infrastructure commune.
- Aucun export : un collecteur OpenTelemetry pourra plus tard lire les mêmes identifiants (SDK Node avec le propagateur W3C, journaux pino) sans changer clients ni partenaires (OBSERVABILITY.md §4).

### 4. Alertes, collecte et tableau de bord dans le dépôt

- `infra/observability/prometheus/alerts.yml` : 22 règles (API absente ou en panne, taux de 5xx, latence p95, retard de la boucle d'événements, tâches en échec / obsolètes / jamais réussies / bloquées, retard et abandons de webhooks, SLA de revue, documents `INFECTED`, clés sans `ACTIVE` ou `STAGED` trop longtemps, écarts / échec / obsolescence / absence de la réconciliation, erreurs de collecte), chacune avec sévérité, résumé, description et `runbook_url` vers une section d'`OBSERVABILITY.md` (signification, première action). Un test parse le fichier et vérifie que chaque métrique citée existe dans `/metrics` et que chaque section de runbook existe.
- `prometheus.yml` : découverte DNS des répliques (`api`), jeton lu dans un fichier (`credentials_file`), règles chargées ; pas d'Alertmanager dans le bac à sable.
- Profil Compose `observability` : Prometheus et Grafana durcis (racine en lecture seule, sans capacités), ports sur loopback, **aucun identifiant par défaut** — les conteneurs refusent de démarrer sans `METRICS_TOKEN` et `GRAFANA_ADMIN_PASSWORD` (≥ 12 caractères), vérification faite **au démarrage du conteneur** (`${VAR:?}` du shell, comme pour MinIO) parce que Compose interpole toutes les variables même hors profil et que la CI valide la pile sans ces variables. Le jeton arrive à Prometheus comme variable du conteneur (la même `METRICS_TOKEN` de `.env` que lit l'API) ; l'entrypoint l'écrit dans un fichier **tmpfs** (`/run/secrets/metrics_token`, mode 0600, le `credentials_file` de `prometheus.yml`) puis la retire de l'environnement avant d'exécuter Prometheus — jamais sur disque, jamais en argument, jamais dans la configuration. Grafana est provisionné (source de données, tableau de bord JSON non modifiable dans l'interface).

## Conséquences

Positives : une panne silencieuse (planificateur arrêté ou jamais démarré, clé jamais activée, webhooks abandonnés, écart de registre) devient une alerte avec sa procédure ; la cardinalité des séries HTTP est bornée par construction ; la base n'est jamais interrogée plus d'une fois par 15 s et par réplique par les collectes, jamais avec plus d'une connexion à la fois, et une base en panne ou verrouillée ne fait tomber ni `/metrics` ni le pool des requêtes de l'API ; le jeton ne transite ni par la configuration de Prometheus, ni par l'environnement de son processus, ni par les journaux ; le mode sans jeton ne peut pas être détourné par un proxy local ; les partenaires reçoivent un identifiant de trace standard ; la fleet peut grandir sans changer la configuration de collecte ; les tests vérifient la cohérence règles ↔ métriques ↔ runbook.

Négatives : les jauges métier sont des instantanés (un état de moins de 15 s peut échapper à deux collectes) ; les collecteurs en série font qu'une base lente sacrifie d'abord les derniers de la liste (visible dans `dfn_metrics_collect_errors_total`) ; les requêtes rejetées par le contrôle d'origine CSRF — middleware d'`AppModule`, appliqué avant celui du module — et les requêtes abandonnées par le client ne sont pas comptées ; `/metrics` répondant 200 ne prouve que le processus, pas la base (d'où `dfn_metrics_collect_errors_total` et `/v1/health`) ; un proxy local qui ne pose aucun en-tête de relais n'est pas reconnu par le mode sans jeton (d'où la consigne d'utiliser le jeton dès qu'un proxy partage la machine) ; la rotation du jeton n'a pas de double validité (quelques 401 le temps du redémarrage) ; pas de notification sans Alertmanager, pas de spans détaillés sans SDK OpenTelemetry ; deux images de plus à suivre (Prometheus, Grafana), avec une rétention locale non sauvegardée ; le profil Compose n'a pas pu être démarré dans l'environnement de développement de cette phase (pas de démon Docker) — `docker compose config` le valide, le premier démarrage par un intégrateur en est la vérification de bout en bout.

## Alternatives

| Alternative                                                                                | Raison du rejet                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Contrôleur Nest `@Public()` pour `/metrics`                                                | Le garde de session recherche tout `Bearer` en base et le limiteur de débit touche Redis : la collecte dépendrait des deux et tomberait avec eux ; un middleware avant les gardes n'en dépend pas                                                                       |
| Intercepteur Nest pour les métriques HTTP                                                  | Ne voit ni les refus des gardes (401/403/429) ni les 404 ; le middleware sur `finish` compte toutes les réponses                                                                                                                                                        |
| Étiqueter l'URL normalisée par expression régulière (UUID → `:id`)                         | Fragile (références, identifiants non UUID), cardinalité non bornée dès qu'un motif échappe ; le gabarit du routeur est exact et fini                                                                                                                                   |
| Jauges mises à jour par les services au fil des écritures                                  | Compteurs par réplique faux dès qu'il y a plusieurs répliques ou une écriture hors API (tâche, CLI) ; la lecture en base donne la vérité partagée, le cache borne le coût                                                                                               |
| SDK OpenTelemetry complet dès maintenant                                                   | Dépendance et collecteur obligatoires pour un bac à sable ; la propagation W3C seule suffit à corréler journaux et partenaires et reste compatible avec un SDK ajouté plus tard                                                                                         |
| `${GRAFANA_ADMIN_PASSWORD:?}` au niveau Compose                                            | Compose interpole les services hors profil : `docker compose up` et la validation CI échoueraient sans la variable ; la vérification au démarrage du conteneur impose la même exigence sans casser la pile                                                              |
| Prometheus en `static_configs: ['api:4000']`                                               | Une seule réplique collectée (première réponse DNS) ; `dns_sd_configs` suit chaque conteneur du service                                                                                                                                                                 |
| Secret Compose `metrics_token` sourcé par `environment:`                                   | Compose n'en fait pas un montage : il copie le secret dans le conteneur créé, ce qu'une racine en lecture seule refuse (« cannot create secret … in read-only service … : `file` is the sole supported option ») — le profil ne démarrait pas                           |
| Secret Compose `metrics_token` sourcé par `file:`                                          | Fonctionne en lecture seule (montage), mais crée une seconde copie du jeton à tenir en phase avec `METRICS_TOKEN` de `.env` (API) : une rotation incomplète donne des 401 silencieux                                                                                    |
| Abandonner `read_only` pour Prometheus                                                     | Affaiblit le durcissement pour contourner une limite de Compose ; le tmpfs écrit par l'entrypoint garde la racine en lecture seule                                                                                                                                      |
| Collecteurs en parallèle (`Promise.allSettled`)                                            | Jusqu'à onze requêtes et connexions par rafraîchissement, et un délai client qui n'annule rien : une table verrouillée faisait s'accumuler des requêtes à chaque collecte jusqu'à épuiser le pool de l'API                                                              |
| Sentinelle (grande valeur) dans `…_last_success_age_seconds` pour une tâche jamais réussie | Une fausse mesure dans une série d'âge ; la série `dfn_maintenance_job_registered` et `unless` expriment « attendue mais absente » sans inventer de valeur                                                                                                              |
| Exclure `/api/metrics` de la réécriture de l'application web (seule mesure)                | Insuffisant seul (tout autre proxy local resterait un pair loopback) et hors du périmètre de l'API ; le refus des requêtes relayées protège quel que soit le proxy — la limitation de la réécriture du web à `/api/v1/*` reste une défense en profondeur complémentaire |
