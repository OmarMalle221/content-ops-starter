# API Diaspora Trust — sandbox

- Base : `http://localhost:4000` (proxy web : `http://localhost:3000/api`)
- Documentation interactive : `GET /docs` (Swagger UI) — export : [`openapi.json`](./openapi.json) (`pnpm --filter @dfn/api openapi:export`)
- Guide partenaires (clés API, scopes, idempotence, webhooks signés) : [`PARTNERS.md`](./PARTNERS.md)
- Toutes les réponses portent `x-dfn-mode: sandbox` et `x-dfn-disclaimer`. **Aucun fonds réel** : financements, règlements de transferts, taux FX, paiements de factures et unités DDA sont simulés.

## Authentification

Deux modes :

1. **Session** (interface web et tests) : cookie `dfn_session` (httpOnly, SameSite=Lax). Obtenir une session : `POST /v1/auth/register` ou `POST /v1/auth/login`. Si `mfaRequired` est vrai, appeler `POST /v1/auth/mfa/verify` avec `code` (TOTP ou code de secours) ou `passkeyAssertion` (défi obtenu par `POST /v1/auth/passkeys/step-up/options`) ; `GET /v1/auth/mfa/status` liste les facteurs disponibles. Connexion sans mot de passe par clé d'accès : `POST /v1/auth/passkeys/authentication/{options,verify}`. Un en-tête `Authorization: Bearer <token de session>` est également accepté pour les tests.
2. **Clé API partenaire** : `Authorization: Bearer dfn_sk_…`. La clé est créée depuis la console `/developers` (`POST /v1/api-credentials`), affichée une seule fois, hachée en base, limitée par **scopes** et par **débit** (`rateLimitPerMinute`). Le contexte obtenu est un membre de l'organisation émettrice uniquement ; les routes d'authentification, d'administration, de simulation et de gestion des clés ne sont jamais accessibles par clé (`403 SCOPE_FORBIDDEN`). Détails dans `PARTNERS.md`.

### Preuve fraîche (step-up)

Les opérations sensibles (autorisation de transfert, baisse des préférences de sécurité, ajout ou révocation d'une clé d'accès, désactivation de la MFA, régénération des codes de secours, approbation ou révocation d'une porte réglementaire) acceptent dans leur corps **soit** `mfaCode` (code TOTP à 6 chiffres ou code de secours `XXXX-XXXX-XX`), **soit** `passkeyAssertion` (réponse WebAuthn à un défi `STEP_UP` de la même session). Un code TOTP n'est accepté qu'une fois (`401 MFA_CODE_REUSED`). Cinq codes erronés bloquent les codes du compte 15 minutes (`423 ACCOUNT_LOCKED`) ; chaque tentative est réservée avant la vérification, une rafale ne fait donc jamais vérifier plus de cinq codes. Activer la MFA (`POST /v1/auth/mfa/enable`) exige `code` **et** `currentPassword` ; les confirmations par mot de passe (activation MFA, changement de mot de passe, ajout de clé d'accès, suppression de compte) comptent dans le verrouillage de connexion. **Liaison à l'opération** (phase 7) : le défi `STEP_UP` se demande avec `POST /v1/auth/passkeys/step-up/options` et un corps `{ operation, resourceId? }` (`transfer.authorize` + id du transfert, `gate.approve` / `gate.revoke` + code de porte, `keys.manage` + finalité ou id de clé, `passkey.revoke` + id de clé d'accès, `passkey.register` (ajout d'une clé d'accès), `mfa.disable`, `mfa.recovery_codes_regenerate`, `security_preferences.lower`, `auth.login_mfa`) ; une assertion présentée pour une autre opération ou une autre ressource est refusée (`403 STEP_UP_OPERATION_MISMATCH`, défi consommé).

### Écritures de support (staff)

Le staff lit les données des organisations dont il n'est pas membre mais ne peut pas les modifier. Une écriture de support exige la permission `admin:support_write` (ADMIN) et l'en-tête `X-Support-Reason: <motif de 10 à 500 caractères>`, journalisé dans l'audit. Elle n'invite jamais son auteur ni un autre membre du staff, n'accorde que le rôle VIEWER (notifié aux OWNER / ADMIN de l'organisation) et ne touche pas aux propriétaires ; supprimer le document d'un autre utilisateur passe aussi par ce motif. Avec `REQUIRE_STAFF_MFA=true`, toute permission staff exige que le membre du staff ait activé la MFA (`403 STAFF_MFA_REQUIRED`). Les destinataires staff choisis par rôle (transferts en revue, contestations, échéances de revue, anomalies de réconciliation, DDA, portes réglementaires) et les assignations d'alertes se limitent alors aux comptes ayant activé la MFA ; la tâche `REVIEW_SLA` traite une alerte assignée à un compte sans MFA comme non assignée.

## Idempotence

Sur `POST`, `PATCH`, `PUT` et `DELETE`, envoyer `Idempotency-Key: <chaîne unique ≤ 255>`. Une même clé avec la même requête (méthode + chemin + corps canonique) renvoie la réponse initiale avec `Idempotent-Replayed: true` ; une même clé avec un corps différent renvoie `422 IDEMPOTENCY_KEY_REUSED` ; une requête encore en cours renvoie `409 IDEMPOTENCY_IN_PROGRESS`. Les réponses sont conservées `IDEMPOTENCY_TTL_HOURS` heures (24 par défaut).

## Format d'erreur

```json
{
  "statusCode": 409,
  "code": "RELEASE_FROZEN",
  "message": "A dispute is open: releases are frozen",
  "details": {},
  "requestId": "…"
}
```

Codes : `VALIDATION_FAILED`, `UNAUTHENTICATED`, `MFA_REQUIRED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `INVALID_TRANSITION`, `RELEASE_FROZEN`, `INSUFFICIENT_FUNDS`, `LEDGER_UNBALANCED`, `RATE_LIMITED`, `ACCOUNT_LOCKED`, `INVITATION_INVALID`, `VERIFICATION_REQUIRED`, `UNSUPPORTED_FILE`, `SANDBOX_LIMIT_REACHED`, `CORRIDOR_UNSUPPORTED`, `QUOTE_EXPIRED`, `DAILY_LIMIT_EXCEEDED`, `JOB_ALREADY_RUNNING`, `JOB_NOT_REGISTERED`, `ACCOUNT_HAS_OPEN_ITEMS`, `DELETION_ALREADY_REQUESTED`, `ACCOUNT_ALREADY_ANONYMIZED`, `NO_DELETION_REQUEST`, `SCOPE_FORBIDDEN`, `API_KEY_INVALID`, `API_KEY_REVOKED`, `API_KEY_EXPIRED`, `IDEMPOTENCY_KEY_REUSED`, `IDEMPOTENCY_IN_PROGRESS`, `NOT_AVAILABLE` ; phase 6 : `MFA_CODE_REUSED`, `RECOVERY_CODE_INVALID`, `STEP_UP_REQUIRED`, `STAFF_MFA_REQUIRED`, `PASSKEY_NOT_FOUND`, `PASSKEY_VERIFICATION_FAILED`, `CHALLENGE_EXPIRED`, `STORAGE_UNAVAILABLE`, `KEY_NOT_FOUND`, `DOCUMENT_INTEGRITY_FAILED`, `LINK_NOT_PENDING`, `ALERT_NOT_ASSIGNABLE`, `GATE_NOT_SATISFIED`, `GATE_SAME_APPROVER`, `PROVIDER_NOT_ACTIVATABLE` ; phase 7 : `KMS_UNAVAILABLE` (503, KMS injoignable ou refus), `KEY_LIFECYCLE_CONFLICT` (409, transition de clé impossible, `details.reason`), `DOCUMENT_INFECTED` (422 à l'envoi, rien n'est stocké ; 409 au téléchargement), `SCAN_UNAVAILABLE` (503, analyseur indisponible, échec fermé), `STEP_UP_OPERATION_MISMATCH` (403, assertion émise pour une autre opération ou ressource) ; `KEY_NOT_FOUND` (503) porte `details.purpose`, `details.keyId` et `details.reason` : `NO_ACTIVE_KEY` (usage sans clé active à l'écriture), `LEGACY_DISABLED`, `KEY_NOT_IN_RING`, ou `DECRYPT_FAILED` (secret MFA illisible) ; au téléchargement, aussi `details.documentId`.

## Montants

Entrée : chaînes décimales (`"18500.00"`). Sortie : `{ "minor": "1850000", "decimal": "18500.00", "currency": "CAD" }`. Devises fiat : CAD, USD, EUR, XOF, GNF. L'unité `DDA` n'apparaît que dans le laboratoire de recherche réservé aux administrateurs.

## Webhooks sortants (résumé)

Événements : `transaction.created`, `transaction.party_accepted`, `funding.confirmed`, `milestone.submitted`, `milestone.released`, `transaction.settled`, `transaction.cancelled`, `dispute.opened`, `dispute.closed`, `transfer.settled`, `transfer.failed`, `invoice.paid`. Charge `{ id, type, createdAt, sandbox: true, data }`, en-têtes `X-DFN-Event`, `X-DFN-Delivery`, `X-DFN-Signature: t=<unix>,v1=<HMAC-SHA256>`, `X-DFN-Mode: sandbox`. Vérification avec `verifySignature` de `@dfn/payment-adapters` (exemples Node et Python dans `PARTNERS.md`). Relances `2^n` minutes jusqu'à `WEBHOOK_MAX_ATTEMPTS`, désactivation automatique après 50 échecs consécutifs, adresses privées refusées.
